Əvvəl spec, sonra kod

Spec-Driven Development-ə praktik giriş: nədir, nə vaxt fayda verir, spec necə yazılır, komandada necə başlamaq olar.

Backend developerlər üçün~15 dəqNümunələr: OpenSpec

01Qısaca

Əvvəl spec review

Ayrıca MR-da, kodsuz. Approve "yazmağa başla" deməkdir.

Kod spec-ə görə

Task-task, özün və ya AI agent. Review kodu spec ilə yoxlayır.

Archive = canlı sənəd

Release-dən sonra spec specs/-ə birləşir: sistem bu gün necə işləyir.

İstifadə et

Yeni servis, endpoint, consumer, schema dəyişikliyi, servislərarası axın, AI-ın çox yazdığı dəyişiklik.

Lazım deyil

Bug fix, config, dependency yeniləmə, incident hotfix.

02Niyə lazımdır?

Spec-siz

  • Ticket gəlir, dərhal kod yazılır
  • 1500 sətirlik MR, reviewer niyyəti diff-dən çıxarır
  • Dizayn müzakirəsi dəyişiklik bahalı olanda başlayır
  • Bir il sonra "niyə?" chat-da itib
  • AI agent prompt-dan təxmin edir

Spec ilə

  • Dizayn 1-2 səhifəlik sənəddə
  • Müzakirə kod yazılmamış olur
  • Spec-i rədd etmək bir saat aparır, günlər yox
  • "Niyə?" repo-dadır
  • Agent razılaşdırılmış müqaviləyə əməl edir

03Spec nədir?

Spec sistemin necə davranmalı olduğunu yoxlanıla bilən şəkildə təsvir edir. Kod onun implementasiyasıdır.
Spec deyil

"OrderPublishService-ə if əlavə et."

Spec-dir

"Status SENT olan sorğu republish edilsə, sistem 409 qaytarmalıdır (SHALL)."

1. Normativ sözlər

SHALL məcburi, SHOULD tövsiyə, MAY istəyə bağlı (RFC 2119).

2. Ssenarilər

Hər tələbin ən azı bir WHEN / THEN ssenarisi.

3. Test olunur

Ssenari testə çevrilmirsə, yenidən yaz.

07Spec yazmaq

## ADDED Requirements

### Requirement: Manual republish of a failed order event
The system SHALL allow a manual republish only when the request status is FAIL.

#### Scenario: Failed request is republished
- **WHEN** an operator calls `POST /v1/orders/{orderId}/republish` for a request in status FAIL
- **AND** the message broker acknowledges the event
- **THEN** the system responds 204
- **AND** the request status becomes SENT

#### Scenario: Request was already sent
- **WHEN** an operator calls republish for a request in status SENT
- **THEN** the system responds 409 with code REPUBLISH_NOT_ALLOWED
- **AND** no event is published

Spec-lər adətən ingiliscə yazılır, çünki alətlər və açar sözlər ingiliscədir.

design.md qərarı

Qərar: sinxron göndər, broker təsdiqini timeout ilə gözlə.

Niyə: status (SENT və ya FAIL) təsdiqdən asılıdır.

Alternativ: fire-and-forget. Rədd: uğursuz göndərişi etibarlı qeyd etmək olmurdu.

Yalnız açıq-aydın olmayan qərarlar üçün.

openspec archive <name>: delta-lar specs/-ə birləşir. Adətən kod MR-ın içində.

Spec MR-da Refs <KEY>, kod MR-da Closes <KEY>. Yoxsa ticket kodsuz bağlanır.

09AI agentlərlə iş

Spec, prompt yox

Agent təsdiqlənmiş spec və tasks.md üzrə, project.md qaydaları ilə işləyir.

Sahibi insandır

Agentin yazdığı spec də review olunur. MR-ı açan müəllifdir.

Səssiz kənarlaşma yoxdur

Spec-dən çıxmaq = əvvəl spec yenilənir və yenidən review olunur.

Hər tapıntını bağla

Düzəlt, trade-off kimi yaz, ya da ticket-ə köçür.

Prompt-da sirr yoxdur

Açar, credential, şəxsi və ya prod data. Yalnız təsdiqlənmiş alətlər.

AI commit-ləri işarələ

Məsələn Co-Authored-By: trailer-i. MR bir oturuşda oxunsun.

💡 Idea grilling: kobud ideyanı agentə ver, əvvəl səni sorğu-suala tutsun. Gizli suallar erkən çıxır.

14FAQ

Spec review ikinci code review deyilmi?

Xeyr. Texniki dizaynın fokuslu müzakirəsidir, bir səhifə böyük diff-dən diqqətlə oxunur. Kiçik dəyişikliklər bir MR-da gedir.

Spec ticket-i əvəz edirmi?

Xeyr. Biznes niyyəti ticket-də qalır. Spec texniki davranış müqaviləsidir.

Sub-task açmağa davam edək?

İstəsəniz. tasks.md texniki bölgüdür.

OpenSpec məcburidirmi?

Xeyr. Artefaktları, review addımını və archive-ı saxla, istənilən alət olar.

AI agent spec-i yaza bilərmi?

Bəli. İnsan yenə review edir və sahiblik edir.

Mövcud servisi tam spec-ə köçürək?

Xeyr. Yalnız yeni dəyişikliklər. specs/ tədricən dolur.
