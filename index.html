Spec first, code second

A practical introduction to Spec-Driven Development: what it is, when it pays off, how to write a spec, and how to start in a team.

For backend developers~15 minExamples: OpenSpec

01TL;DR

Spec reviewed first

In its own MR, with no code. Approval is the green light to build.

Code follows the spec

Task by task, by you or an AI agent. Review checks code against the spec.

Archive = living docs

After release the spec merges into specs/: how the system works today.

Use it

New services, endpoints, consumers, schema changes, cross-service flows, AI-heavy changes.

Skip it

Bug fixes, config, dependency bumps, incident hotfixes.

02Why bother?

Without a spec

  • A ticket arrives, coding starts right away
  • A 1,500-line MR, the reviewer reverse-engineers intent
  • The design debate starts when change is expensive
  • A year later, "why?" is lost in chat
  • The AI agent guesses from a prompt

With a spec

  • Design is a 1-2 page document
  • Debate happens before any code exists
  • Rejecting a spec costs an hour, not days
  • "Why?" lives in the repo
  • The agent follows an agreed contract

03What is a spec?

A spec describes how the system must behave, in a way you can verify. The code is its implementation.
Not a spec

"Add an if to OrderPublishService."

A spec

"When a request in status SENT is republished, the system SHALL respond 409."

1. Normative words

SHALL must, SHOULD recommended, MAY optional (RFC 2119).

2. Scenarios

Every requirement has at least one WHEN / THEN.

3. Testable

If a scenario cannot become a test, rewrite it.

04When to use it

ChangeSpec?
New service or capabilityYes
New endpoint, consumer, schema change, cross-service flowYes - sweet spot
An AI agent writes most of the codeYes
Refactoring with no behavior changeOptional
Bug fix, config, dependency bump, one-linerNo
Production incident hotfixNever
The one rule that matters: if a change needs a spec, do not start implementing until the spec is approved. Small changes may put spec and code in one MR, spec commits first.
Writing a spec for a one-liner means you are doing it wrong. SDD is a design habit, not bureaucracy.

07Writing a spec

## ADDED Requirements

### Requirement: Manual republish of a failed order event
The system SHALL allow a manual republish only when the request status is FAIL.

#### Scenario: Failed request is republished
- **WHEN** an operator calls `POST /v1/orders/{orderId}/republish` for a request in status FAIL
- **AND** the message broker acknowledges the event
- **THEN** the system responds 204
- **AND** the request status becomes SENT

#### Scenario: Request was already sent
- **WHEN** an operator calls republish for a request in status SENT
- **THEN** the system responds 409 with code REPUBLISH_NOT_ALLOWED
- **AND** no event is published

Bad vs good

BadGoodWhy
"Errors must be handled properly""No broker ack within 30 s: the system SHALL mark the request FAIL""Properly" is untestable
"Create an OrderEventHandler class""A duplicate event SHALL NOT create a new request"Behavior, not classes
A requirement with no scenarioAt least one WHEN/THENNo scenario, no test
Five cases in one scenarioOne case per scenarioScenario = test

proposal.md template

# Proposal: <short title>
Ticket: <KEY>.

## Why
<problem, why now>

## What Changes
- <behavior change>
- <what does NOT change>

## Capabilities
### New / Modified
- `<name>`: <one sentence>

## Impact
- <services, config, DB, contracts>

design.md decision

Decision: publish synchronously, wait for the broker ack with a timeout.

Why: the status (SENT or FAIL) depends on the ack.

Alternative: fire-and-forget. Rejected: a failed send could not be recorded reliably.

Only for decisions that are not obvious.

08The lifecycle of one change

Click a step.

Proposechange folder

Create openspec/changes/<name>/ with proposal, spec deltas and tasks. Link the ticket.

Validate--strict

Run openspec validate <name> --strict. Fix every error before asking for review.

Spec reviewno code

An MR with only the change folder. Approval means "go build it".

Implementfrom tasks.md

Tick tasks off. New scope? Update the spec first, re-validate, then code.

Code reviewvs the spec

A normal MR linking the change folder. The reviewer checks code against the approved scenarios.

Archiveafter release

openspec archive <name>: deltas merge into specs/. Usually inside the code MR.

Refs <KEY> in the spec MR, Closes <KEY> only in the code MR. Otherwise the ticket closes with no code.

09Working with AI agents

Spec, not prompt

The agent works from the approved spec and tasks.md, following project.md.

A human owns it

Agent-written specs get the same review. Whoever opens the MR is the author.

No silent drift

Leaving the spec means updating the spec first and re-reviewing.

Close every finding

Fix it, document the trade-off, or move it to a ticket.

No secrets in prompts

Keys, credentials, personal or production data. Approved tools only.

Mark AI commits

For example a Co-Authored-By: trailer. Keep MRs readable in one sitting.

💡 Idea grilling: give the agent your rough idea and ask it to question you first. Hidden questions surface early.

11Worked example: tasks.md

## 1. API
- [ ] 1.1 Add POST /v1/orders/{orderId}/republish - verify with controller test for 204/404/409
- [ ] 1.2 Map error codes to responses - verify with error-handler test

## 2. Logic
- [ ] 2.1 Allow republish only from FAIL - verify with service test per status
- [ ] 2.2 SENT on broker ack, FAIL on timeout - verify with broker stub test

## 3. Docs
- [ ] 3.1 Update the API description
Every task ends with "verify with ...": the test that proves it.

14FAQ

Isn't spec review just a second code review?

No. It is the one focused discussion of the technical design, and one page is read far more carefully than a big diff. Small changes share one MR.

Does the spec replace the ticket?

No. Business intent stays in the ticket. The spec is the technical behavior contract.

Should we keep creating sub-tasks?

If you like. tasks.md is the technical breakdown.

Is OpenSpec required?

No. Keep the artifacts, review step and archive; any tool works.

Can an AI agent write the spec?

Yes. A human still reviews and owns it.

Spec the whole existing service?

No. Only new changes. specs/ fills up over time.
